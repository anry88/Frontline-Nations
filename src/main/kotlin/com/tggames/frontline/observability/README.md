# Observability package

`PlayerJourney` writes the versioned server-side product path to `player_journey_events`. The event table references a surrogate `analytics_players.id`, not the player's Telegram identity, and snapshots normalized attribution, locale, country, the confirmed internal-account flag, and bounded step fields. It never stores message text, callback payloads, names, or the player's Telegram ID. The Telegram update ID is retained only as the idempotency key. Events are written inside the same transaction as the accepted Telegram update and the related business mutation. The `(telegram_update_id, event_sequence)` constraint prevents a repeated update from duplicating a path.

A session starts with a user-driven bot action and continues while the gap from the previous recorded event is less than 30 minutes. Session end is derived from inactivity; background delivery and scheduled jobs do not create activity. Coverage begins when migration V20 is deployed. Earlier funnel steps are deliberately left absent instead of being reconstructed from aggregate command counters.

`FRONTLINE_ANALYTICS_INTERNAL_TELEGRAM_IDS` is a comma-separated list of owner or controlled test accounts confirmed by the operator. Their events remain queryable with `is_internal = TRUE`, while product gauges and external cohort queries exclude them by default. The value belongs only in the private deployment environment. Events default to 400 days of retention and are removed by the daily cleanup job; configure the duration with `FRONTLINE_ANALYTICS_EVENT_RETENTION_DAYS`. Direct database access remains limited to operators and the application account.

`TechnicalOperationTelemetry` records each battle calculation/result-delivery and replay preparation/delivery attempt in `technical_operation_attempts` plus its ordered stage rows. Those writes use independent transactions, so engine, FFmpeg, timeout, restart, and Telegram failures remain observable when the gameplay transaction rolls back. Personal battle results are delivered only after the gameplay transaction commits. Replay stages distinguish requested, queued, cold render started, ready, cache hit, and Telegram delivered; ready and delivered never imply that the player watched the video. An incomplete attempt is marked `restart` on boot or `timeout` after 15 minutes. Technical rows use the same 400-day cleanup policy as journey events.

V22 derives `analytics_player_activation`, `analytics_retention_cohorts`, and `analytics_dropoff_report` from captured events. The activation funnel counts distinct battle IDs, so a repeated callback cannot become a second battle. D1/D3/D7 use exact `[k×24h,(k+1)×24h)` user-action windows and exclude immature players. Thirty minutes without activity ends a session but does not prove churn. The default views exclude internal accounts; matching `*_all` views retain them for an explicit audit. `analytics_external_event_sequences` exposes a surrogate-only diagnostic sequence for restricted database access. Detailed cohort/source/referral/locale/country/result/loss/variant cuts live in `docs/analytics/activation-retention.sql`, where `n < 30` is marked descriptive.

The V23 guided first mission records the variant on actual CTA display/click and the accepted battle events. The battle snapshot separately records whether orders were accepted as recommended, customized from the card, or entered through the regular flow. A configured fallback reports the actually shown `legacy` variant while preserving the player's stable stored assignment.

V24 stores the state-aware primary action selected for each personal battle result and distinguishes Telegram-confirmed delivery, explicit detail opening, action click, and completed next step. Repeated detail opens increment a counter without changing the first-open timestamp. Telegram has no passive read receipt, so `sent_at` and `details_opened_at` must not be merged. The three action names and their sent/clicked/completed states are fixed low-cardinality product dimensions; owner/test accounts are excluded through `analytics_players`.

Army recovery emits fixed blocked, started and completed journey events. Product gauges count distinct external players who encountered a blocker, restored readiness, and started a later battle in the same session or within 24 hours; p50/p90 measure observed time from the first blocker to readiness. The events describe server-observed state transitions rather than an inferred reason for leaving.

V26 adds fixed `front_bridge_shown`, `front_bridge_clicked`, `contribution_committed`, `contribution_withdrawn`, and `personal_battle_blocked_by_reservation` steps. `frontline.product.front.bridge.players{status=...}` reports distinct external players at shown, clicked, first contribution, withdrawal, later-session return, and reservation-block guardrail states. Shown is written only after Telegram accepts the bridge message; it remains delivery evidence rather than a read receipt. The once-per-player offer row provides the shown/clicked denominator, while journey rows preserve session analysis without exposing Telegram identity in metric labels.

V27 adds one feedback row per campaign and player. `frontline.product.feedback.players{status=...}` reports the bounded `inline_offered`, `nudge_sent`, `opened`, `answered`, `skipped`, and `commented` states; `frontline.product.feedback.reason{reason=...}` uses only the seven fixed reason codes. Default feedback views exclude configured internal accounts and expose no comment text. `analytics_feedback_comments_restricted` contains optional text under the surrogate analytics identity for restricted operator review and the cleanup job removes it after the configured retention period.

Navigation errors store only a fixed category, fixed player stage and fixed recommended recovery action. The raw message, slash command and callback payload are never stored or exported as labels. Gauges show the bounded category/stage matrix plus distinct external players who recovered through a later successful event in the same session or produced repeated errors.

`GameMetrics` owns low-cardinality Micrometer instruments for the Telegram command UI, while `ProductAnalyticsMetrics` publishes global activation, repeat, exact-window retention, observed-stop, TTFB, coverage, feedback, post-battle action, front-bridge, and result-engagement gauges. Both refresh database-backed gauges once per minute. Player, registration, country, Stars, equipment, battle, journey, and technical/product metrics exclude confirmed internal accounts. Active-player gauges count distinct external players with a persisted `user_action` event, rather than `players.updated_at`. The player-by-country gauge is bounded by the versioned 250-entry alliance catalog and exposes the neutral country code plus its English display name. `frontline.journey.events` and `frontline.journey.players` expose only the fixed event enum and the fixed `day/week/month/total` periods. `frontline.technical.stage` is the attempt/error denominator; `frontline.technical.stage.duration` is a Prometheus histogram used for p50/p95/p99. `frontline.replay.queue.pending` and `frontline.replay.queue.active` expose bounded worker pressure without identifying a player or battle. Technical operation, mode, stage, result, failure, and cache labels all come from fixed bounded enums. Detailed product dimensions remain in PostgreSQL rather than becoming a high-cardinality Prometheus cross-product. Event labels must stay bounded: never add Telegram IDs, nicknames, raw `/start` payloads, payment charge IDs, battle IDs, attempt IDs, session IDs, or callback data as tags.

Prometheus naming is derived from Micrometer names. For example, the `frontline.bot.command` counter is exported as `frontline_bot_command_total`. Persistent gauges are rebuilt from the database so dashboard totals survive application restarts; event counters represent activity observed by the current Prometheus history.
